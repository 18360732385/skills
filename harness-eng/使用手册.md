## 1. 这个技能是做什么的？

**harness-eng** 把「Agent Harness 工程化」做成可重复的施工仪式：探测仓库 → 推荐配置 → 你确认 → 再往目标仓写入去域化模板。

它落地的不是某业务系统的私有规范，而是一套**跨仓可复用**的协作骨架：

| 能力 | 落在哪 | 作用 |
|---|---|---|
| 协作入口 | 根/分册 `AGENTS.md`、总览规则 | Agent 一进仓就知道命令、红线、文档优先级 |
| 契约骨架 | `docs/func|api|db|redis|jobs` + path-scoped rules | 「改代码前读真相、改后回写文档」有落点 |
| 知识回流 | `docs/agent-kb` | pitfalls / 架构概览 / 已知缺口可沉淀 |
| 规划与软门禁 | `docs/superpowers` + hooks | 进行中事项可见；提交前软提醒（不拦截） |
| 工具连接样例 | `mcp.json.example` 等 | 教怎么接 MCP，真密不入库 |
| 多工具配置 SSOT（可选 L5） | `docs/agent-config/` + `sync.mjs` | 一份真相生成 Cursor / Claude / Qoder 等目录 |

施工现场（评分、报告、填充进度）默认在目标仓的 `docs/harness-eng/`。

### 解决了什么问题？

没有 harness 时，常见痛点是：

1. **每个 AI 工具各写一套规则**，Never do / 契约互相漂移，换工具就丢上下文。  
2. **文档和代码脱节**：接口、库表、Redis Key 只在人脑里，Agent 只能猜。  
3. **「装了很多 markdown」≠「可以放心 AI 改业务」**：空壳、TODO、未验收片段被当成真相。  
4. **大仓第一次工程化路径过长**：探测、骨架、MCP、inventory、精填、验收、打分没有统一流水线。

harness-eng 用阶梯（L0–L5）+ 确认闸门 + 填充/打分协议，把上述问题收成可审计、可续跑、可度量的工程过程。

**一句话**：技能负责「把仓库改造成适合多 AI 工具协作的工程形态」；业务真相仍由你们（或 Agent 按 Plan 精填）写进 `docs/**`，各工具只挂薄入口。

## 2. 如何安装和更新

技能本身装在 **当前 Agent 宿主的用户级 skills 目录**（保证 `SKILL.md` 在技能根目录）；施工产物写在 **业务目标仓**（二者不要混淆：装 skill ≠ 给业务仓落地 harness）。用户可能用 Cursor、Claude Code、Qoder、Trae、Codex 等，**不要默认装到某一家的目录**。

### 2.1 一句话安装（推荐）

对当前对话里的 Agent 说：

```text
帮我把这个 skill 装到你当前 Agent 宿主的用户 skills 目录，地址：
https://github.com/18360732385/skills/tree/main/harness-eng
保证目录内直接有 SKILL.md，装完告诉我实际路径。
```

也可自己跑 CLI（全局；若提示复制/软链，优先 **Copy**）。`--agent` 按你用的宿主传，不要默认写成某一家：

```bash
npx skills add https://github.com/18360732385/skills/tree/main/harness-eng -g
# 需要指定宿主时加上：--agent <host>
```

装好后：**新开 Agent 会话**，再显式点名 **harness-eng**。

常见用户 skills 目录（示例，以宿主实际加载目录与官方文档为准）：

| 宿主 | 用户 skills 目录示例 |
|---|---|
| Cursor | `~/.cursor/skills/` 或 `~/.cursor/skills-cursor/` |
| Claude Code | `~/.claude/skills/` |
| Codex / Qoder / Trae / 其他 | 按该宿主文档 |

分支提示：上述 URL 指向 `main`；若要跟踪施工主干，可把路径改成仓库当前发布分支（如 `V0.5.X`）。

### 2.2 一句话更新

```text
帮我更新本机的 harness-eng skill：从
https://github.com/18360732385/skills/tree/main/harness-eng
覆盖安装到你当前 Agent 宿主的用户 skills 目录（保留备份或直接覆盖均可），完成后核对 SKILL.md / manifest 版本。
```

或再次执行上面的 `npx skills add ...`（按宿主传 `--agent`），然后新开会话。目标仓 `docs/harness-eng/harness-meta.yaml` 的 `skill_version` 可随后续 resume / upgrade 对齐。

### 2.3 从本源仓使用（开发 / 自测）

若你就在含 `harness-eng/` 的 skills 仓库里对话，直接点名技能即可。路径因宿主而异，常见为：

- 仓库内：`harness-eng/`（本仓布局）
- 或已拷到某宿主用户目录：`<host-skills-dir>/harness-eng/`

### 2.4 手动拷贝安装

把同一目录拷到 **当前宿主的用户 skills 目录**，保证 `<host-skills-dir>/harness-eng/SKILL.md` 直接存在：

```powershell
# Windows
Copy-Item -Recurse -Force <源>\harness-eng <host-skills-dir>\harness-eng
```

```bash
# macOS / Linux
cp -R <源>/harness-eng <host-skills-dir>/harness-eng
```

路径示例（非唯一）：Cursor 常见 `~/.cursor/skills/harness-eng`（或 `skills-cursor`）；Claude Code 常见 `~/.claude/skills/harness-eng`；其余按该宿主文档。

### 2.5 前置条件

- 本机可用 **Node.js**（渲染、打分、验收、报告等脚本为 `.mjs`）。  
- 写盘前必须过 **确认闸门**（见下文）；审计模式默认不写文件。  
- 多工作区 / 多模块仓要先确认 **目标根目录**，技能只写已确认的根。  
- 一句话安装装的是 **skill 文件**；要给业务仓施工，需另说「流水线 / 落地 / 审计」等。

## 3. 如何使用（自然语言即可）

不必背内部模式名。对 Agent **点名 harness-eng**，再用场景话描述意图即可。

### 3.1 按场景怎么说

| 你想做什么 | 可以这样说 | Agent 大致会走 |
|---|---|---|
| 大仓第一次全面工程化 | 「用 harness-eng 跑**流水线**，目标 L4」 | audit → L4 骨架 → MCP 矩阵/闸 → 填充计划 → 多 Agent 精填 → 打分 / HTML 报告 |
| 只想看缺什么、先别改仓 | 「**审计**一下本仓 harness 成熟度」 | 对照 L0–L5，默认不写盘 |
| 从零或按阶梯装骨架 | 「给这个仓**落地** harness，做到 L2，域只要 api 和 db」 | 探测 → 推荐包 → 提问 → WritePlan → **等你确认** → 渲染 |
| 已经装了一半 | 「**续跑**补齐缺口，不要覆盖我已有的 Never do」 | 读 meta，只补缺，`on_exists=skip` |
| 升一阶 | 「从现在完整阶**升阶**到 L3」 | 按 upgrade 规格差分补齐 |
| 深填契约真相 | 「按 fill-plan 做**多 Agent 填充**」 | 过填充 MCP 闸 → 批次精填 → acceptance → merge → score |
| 能不能开 AI 改业务 | 「跑**完整度打分** / **开干闸**」 | 看 `ai_coding_ready`，打开 `docs/harness-eng/report-latest.html` |

不确定选项时，在提问批次里回复 **「全部推荐」**：按探测结果的推荐包收齐答案；**写盘仍要再确认一次**（或先说预授权）。

### 3.2 标准施工节奏（落地 / 流水线）

1. **探测**：指纹仓库类型（空仓 / 半成品 / 已成熟 / 已有 Claude 外源等）。  
2. **推荐包**：给出 RecommendedProfile（阶梯、契约域、分册、AI 工具面等）。  
3. **提问**：每批尽量 ≤5 题；可「全部推荐」。  
4. **WritePlan**：白话摘要 + 文件动作表 + 渲染预览。  
5. **确认闸门**：你明确说确认类词语之后，才真正写盘。  
6. **自检与移交**：对照阶梯清单；打印分级 TODO（密钥泄露、空壳补真相等）。

### 3.3 确认与预授权（写盘前必过）

在下列**任一**回复之前，Agent **不应**往目标仓写 harness 文件：

- `确认` · `确认写入` · `按计划执行` · `执行 WritePlan` · `LGTM`

也可子集确认，例如：`只执行 L0`、`去掉 14 后执行`。

若首轮同意 **预授权**，同会话后续的 resume / fill 可自动写盘；否则每一轮填充仍要确认。词表以技能内 [write-plan.md](modes/write-plan.md) 为准。

### 3.4 推荐最短路径（大仓）

用自然语言串起来即可：

1. 「点名 harness-eng，跑流水线，目标 L4，填充用 agents，金标批次。」  
2. 「全部推荐 → 确认预授权 → 确认。」  
3. 骨架与 MCP 闸过完后，继续填充战役；验收合并后打开 `docs/harness-eng/report-latest.html`。  
4. 看报告上的 **开干（ai_coding_ready）** 与 **金标达标率（gold_ratio）**；启发式草稿只留在 `.fill-work`，不要当 SSOT。

### 3.5 本地脚本（可选，不经过对话）

在 **harness-eng 技能目录**执行（`--root` 指向业务目标仓；目标仓若已渲染出同名脚本也可就地跑）：

```bash
cd <harness-eng技能目录>
node scripts/fill-plan.mjs --root <目标仓> --init --gold --sample-n 30
node scripts/fill-score.mjs --root <目标仓>
node scripts/fill-report-html.mjs --root <目标仓> --score docs/harness-eng/score-latest.json
node scripts/acceptance-check.mjs --root <目标仓> --domain api
node scripts/selfcheck.mjs
```

Windows 下向脚本传 JSON 时，注意转义问题（见 write-plan 中的 Windows JSON 传参说明）。

## 4. 支持哪些 AI 编程工具？

真相与契约只维护 **一份 SSOT**：`AGENTS.md` + `docs/**`。  
各 AI 产品只生成 **入口适配**（短指针 / 薄规则），业务红线与 Pn **不**复制多份。

### 4.1 内置适配

| 工具 | 内部 ID | 常见探测信号 | 典型生成入口 |
|---|---|---|---|
| **Cursor** | `cursor` | `.cursor/` | L0 rules / AGENTS；可选 `.cursor/rules/00-harness-ssot.mdc` |
| **Claude Code** | `claude` | `CLAUDE.md` / `.claude/` | 根 `CLAUDE.md` + L3+ 全量 `.claude/rules/*.md` 镜像 |
| **Codex** | `codex` | `.codex/` | `.codex/harness.md` + `contract-sync.md` 指针（**部分对齐·不默认 / P2**，hooks/MCP **未**全量同步，未探测不进「全部推荐」） |
| **Qoder** | `qoder` | `.qoder/` | `.qoder/rules/00-harness-ssot.md` + L3+ 全量 rules 镜像（`.md`） |
| **Trae** | `trae` | `.trae/` | `.trae/rules/00-harness-ssot.md` + L3+ 全量 rules 镜像（`.md`） |
| **WorkBuddy / CodeBuddy** | `workbuddy` | `.codebuddy/` / `CODEBUDDY.md` | `CODEBUDDY.md` + rules 镜像 + L3+ Claude 系 hooks 全家桶 |

提问时对应 `Q_AI_TOOL`，**可多选**。未探测到任何工具时，「全部推荐」的 `ai_tools` 为空，须追问一次；**不**默认 Cursor，也不把 Codex 塞进默认包。Codex 选项标注 **部分对齐·不默认**（仅探测到 `.codex/` 或显式勾选才纳入）。

### 4.2 自定义工具

可回复类似：

```text
自定义: 工具名=FooAgent; 入口路径=.foo/RULES.md
```

技能会在该路径写入指针模板（入口路径须你给出或确认）。自定义工具**不会**自动装配宿主 hooks。

### 4.3 软门禁与 hooks / MCP 差异（L3+）

按**协议族**理解（详 [ai-tools.md](host/ai-tools.md)）：

| 族 | 工具（`ai_tools`） | hooks（L3+） | MCP example（L4+） |
|---|---|---|---|
| **Cursor 族** | `cursor` | `.cursor/hooks.json` + 脚本；支持 hooks 家族（扩展 commit 门禁、MySQL 护栏、编辑提醒、stop 清单等） | `.cursor/mcp.json.example` |
| **Claude 族** | `claude` | `.claude/settings.json`（只 merge hooks 段）+ `claude-adapter.js` | 根 `.mcp.json.example` |
| | `qoder` | `.qoder/settings.json`（Claude 系）+ adapter | 根 `.mcp.json.example` |
| | `trae` | `.trae/hooks.json`（Claude 系嵌套）+ adapter | `.trae/mcp.json.example` |
| | `workbuddy` | `.codebuddy/settings.json`（Claude 系 **全家桶**）+ adapter | 根 `.mcp.json.example` |
| **部分对齐** | `codex` | `.codex/hooks.json` + 基础 commit gate | 见 [templates/ai-tools/adapters/codex.md](templates/ai-tools/adapters/codex.md) |
| **兜底** | 任意 L3+ | 建议 `git config core.hooksPath .githooks`，仓外直接 `git commit` 也有软提醒 | — |

软门禁一律 **fail-open**（提醒不拦截提交）。**真密**由 fill-mcp 写入（路径 SSOT：`scripts/lib/mcp-paths.mjs`），L4 只落 example。

### 4.4 0.5.2+ 多宿主对齐（摘要）

| 变更 | 说明 |
|---|---|
| **MCP 多路径** | 按工具读 `.cursor/mcp.json` ∥ 根 `.mcp.json` ∥ `.trae/mcp.json`（见 `mcp-paths.mjs`） |
| **Claude 全量 rules 镜像** | L3+ 把 `.cursor/rules/*.mdc` 镜像到 `.claude/rules/*.md` |
| **CodeBuddy 升格** | `workbuddy` 与 Cursor 族对等装配 hooks 家族 + 根 MCP example |
| **适配卡** | 各工具路径细节：[templates/ai-tools/adapters/](templates/ai-tools/adapters/) |
| **L5 生成引擎** | [sync-hosts.md](host/sync-hosts.md) + `scripts/agent-config/sync.mjs` |

### 4.5 对齐矩阵（0.5.7+）

| 工具 | 对齐程度 | 不要误读成 |
|---|---|---|
| Cursor / Claude / Qoder / WorkBuddy | **高** | — |
| Trae | **中高** | 不是低配、也不是「未对齐」 |
| Codex | **部分（P2）·不默认** | **不是**已全量同步 rules/hooks/MCP；未探测不进「全部推荐」 |

`1x-contract-sync` 只给拿不到全量 `*-sync*` 镜像的宿主（尤其 Codex、自定义入口、L0–L2）。L3+ / L5 全量镜像宿主不再强制再写一份 alwaysApply 1x。权威始终是根 `AGENTS.md` + `docs/**`，外加**本宿主** rules 目录（若有）；`.cursor/rules/11|12|13|16` 只是 Cursor 示例。详 [ai-tools.md](host/ai-tools.md)。

选 **Codex + L5** 时：`sync.mjs` **不会**全量发出 Codex 的 rules / hooks / MCP / skills（**部分对齐 P2 · 不默认**）。详见 [adapters/codex.md](templates/ai-tools/adapters/codex.md)。

## 5. 一个仓库如何同时支持多套 AI 工具？

核心原则：**契约一份，入口多份，生成物可同步。**

### 5.1 落地时多选 AI 工具面

在提问 `Q_AI_TOOL` 时勾选 Cursor + Claude + Qoder + Trae…  
确认写入后，技能会：

- 为每个已选工具生成对应适配文件；  
- 把 `ai_tools` 列表记入 `docs/harness-eng/harness-meta.yaml`；  
- 对**不全量镜像**的宿主写入 **契约 sync 指针**（Codex 始终；claude/qoder/trae/workbuddy 仅 L0–L2）；L3+ / L5 全量镜像宿主不再强制冗余 `1x`；  
- **不删除**未选工具目录里你已有的用户文件（续跑时 skip；遗留 1x 亦不自动删）。

### 5.2 已有 Claude / 外源规则时（FOREIGN）

若仓里已有 `CLAUDE.md` / `.claude/` 但还没有本 harness 结构，会走并存策略（`Q_COEXIST`），例如：

- **保留 CLAUDE 并存**：不动 Claude 文件，另装 AGENTS / rules / 契约；冲突裁决写进 AGENTS。  
- **逐步迁到 AGENTS**：暂留 Claude，迁移完成后你再决定是否归档。  
- **只加契约与 agent-kb**：不强装根 AGENTS / alwaysApply 规则。

删除 `CLAUDE.md` 必须你书面确认，技能默认不删。

### 5.3 多工具长期维护：升到 L5（推荐）

当一个仓同时服务多种 AI 产品时，【推荐】启用 **L5 配置 SSOT 管线**：

- 单一真相：`docs/agent-config/`（rules / hooks / mcp / settings / skills）  
- 生成器：`scripts/agent-config/sync.mjs`；用 `--check` 查漂移  
- 生成物：`.cursor/*`、`.claude/*`、`.qoder/*`、`.trae/*`、`.codebuddy/*` 等带 GENERATED 标记 → **勿手改**；改 SSOT 再 sync  

这样「改一处规则、多工具目录一致」，比在每个产品目录里手工复制安全得多。

### 5.4 协作纪律（给团队的约定）

1. 业务 Never do、接口/库表真相只改 `AGENTS` / `docs/**`。  
2. 各工具入口文件只保留「指向 SSOT」的薄指针。  
3. MCP **真密**只放本机/本仓约定位置，example 可入库；默认 gitignore 真密 `mcp.json`。  
4. 填充与打分以文件系统 + Node 脚本为准，与当前打开的是 Cursor 还是 Claude **无关**。

## 6. 如何确认「工程化完成程度」够支撑 AI Coding？

### 10 秒结论（首页标准）

| 你在仪表盘上看到 | 是否可以宣称 AI Coding |
|---|---|
| **决策台**徽章 = **「建议可以开干」**，且 KPI **可 AI coding / 开干 = YES**（`ai_coding_ready`） | **可以**（仍须人工审契约与代码） |
| 徽章 = 「建议暂缓」，或开干 = NO / 有 blockers | **不可以** |
| 仅阶梯到了 L4、或「仪表参考分 / overall」很高 | **不可以**（趋势台已标明参考分 **≠开干**） |
| **金标达标率（gold_ratio）** 很高，但开干仍 NO | **不可以**（金标不替代开干闸） |

权威页面：目标仓 `docs/harness-eng/report-latest.html`（由 `fill-score` + `fill-report-html` 生成；模板见技能内 `templates/report/harness-report.html.tmpl`）。

### 先分清两件事

| 概念 | 含义 | 够不够 AI 改业务？ |
|---|---|---|
| **阶梯齐套（L0–L4/L5）** | 协作入口、契约骨架、kb、hooks、MCP example 等文件在不在 | 只说明「脚手架在」；**不等于**可以开干 |
| **开干闸 `ai_coding_ready`** | 骨架就绪 ∧ 覆盖达标 ∧ 语义抽检过 ∧ fill-plan 批次全关，再叠加 gate_profile | **唯一**对外宣称「建议可以 AI 改业务」的闸 |

旧字段 `ready.ok`、形态分 `overall`、贴顶信号 `formula_ceiling` **都不是**开干依据。

### 6.0 对话内会话仪表盘（工程轮末尾）

0.5.4+：点名 **harness-eng** 且本轮是**目标仓施工 / harness 工程**时，Agent 回复末尾附「## harness-eng 会话仪表盘」——与 HTML 四台同源的决策 / 诊断 / 任务 / 趋势摘要，并附 mermaid 象限图（有 score 时）。纯问版本号、安装、手册、术语、技能本身（无 land/audit/pipeline/fill 意图）则**整块省略**。工程模式仍在进行时（例如正等 WritePlan 确认），中途 meta 问仍附仪表盘。含糊默认不附。规格 [session-dashboard.md](modes/session-dashboard.md)。

| 元素 | 含义 |
|---|---|
| 四台表 | 会话内轻量快照；开干结论仍只看决策台 `ai_coding_ready` |
| **详情请查询仪表盘** | 链到目标仓 `docs/harness-eng/report-latest.html`（已生成可点击） |
| [使用手册.html#s6](使用手册.html#s6) | 四台完整读法（本手册第 6 章） |

脚本（只读）：`node scripts/session-dash.mjs --root <目标仓> --intent engineering`（`--intent meta` 不输出 markdown）。规格 [session-dashboard.md](modes/session-dashboard.md)。

### 6.2 仪表盘四台：看什么、到什么程度算 AI Coding

仪表盘顶部有四个 Tab（决策台 / 诊断台 / 任务台 / 趋势台）。**能否 AI coding 只看决策台**；其余台用来解释「差在哪、下一步做什么」。

#### 决策台（唯一开干裁决）

页面文案：**「10 秒结论：能否开干、差什么、下一步做什么。」**

| 界面元素 | 达到什么程度 | 含义 |
|---|---|---|
| **Verdict 徽章** | 显示 **「建议可以开干」** | 内部 `ai_coding_ready=true`；可开始用 AI 协助改业务 |
| | 显示 **「建议暂缓」** | 未达开干；看 headline / hint / blockers |
| **KPI：可 AI coding / 开干** | **YES** | 与徽章一致；仪表盘「开干」**只看此项** |
| **KPI：金标达标率**（有 SSOT 时） | 越高越好 | acceptance 通过占比；**大仓进度参考，不替代开干** |
| **headline / hint / 差距行** | blockers 清空 | 列出 skeleton / coverage / semantic / fill-plan / gate 缺口 |
| **下一步动作列表** | 按列表执行后重新打分 | 对齐 fill-plan / agents |

开干为 YES 时，底层需同时成立（决策台 blockers 为空）：

1. **骨架就绪 `skeleton_ready`**：常见为 L4 阶梯与 hooks / MCP example 等必备齐。  
2. **覆盖就绪 `coverage_ready`**：相对 inventory 达目标仓 `docs/harness-eng/score-policy.yaml`（无文件时回退 meta / CLI 默认）。  
3. **语义就绪 `semantic_ready`**：acceptance / 语义抽检无不可接受 blocker。  
4. **填充计划全关 `fill_plan.all_closed`**：无 Plan 或仍有开放批次 → 开干强制 NO。  
5. **`gate_profile` 下的 gate.\***：阈值以 score-policy 与 [fill-gate.md](fill/fill-gate.md) 为准（strict / gold 数值会随版本调整，**勿背手册硬编码**）。

> 速查：新仓【推荐】`gate_profile=strict`；贴顶后可升 `gold`。具体覆盖率、形态地板、TODO 扫面等以当次 score JSON 的 blockers 与 policy 文件为准。

#### 诊断台（解释「为什么还不能开干 / 哪域拖后腿」）

| 界面元素 | 怎么用 | 与 AI Coding 关系 |
|---|---|---|
| 覆盖条 / 形态条 | 看分域覆盖与形态是否贴顶 | 覆盖未达 policy → 开干 NO；形态贴顶但开干 NO → 去关 Plan / 清语义 / gate，**勿空追 overall** |
| 四域形态分 vs 分域上限 | 哪域远离上限 | 指导精填优先级，**单独拉高形态分不会让徽章变「建议可以开干」** |
| 常见缺口 miss / 低分真相 Top | 缺章、占位、幽灵端点等 | 对应 fill-truths-agents 批次 |

#### 任务台（下一步补文档）

| 界面元素 | 怎么用 | 与 AI Coding 关系 |
|---|---|---|
| 分片任务网格 `next_shards` | 下一批可执行补文档任务 | 做完并 acceptance → merge → 再打分；空台通常要先 fill-plan / inventory |

#### 趋势台（进度，不是开干）

| 界面元素 | 怎么用 | 与 AI Coding 关系 |
|---|---|---|
| **仪表参考分** | overall / 综合参考 | 页面明确 **≠开干** |
| overall / coverage 趋势、相对上次 diff | 看施工是否在涨 | 趋势变好仍可能开干=NO |

### 6.3 对照表：仪表盘读数 → 行动

| 决策台状态 | 典型伴随现象 | 建议行动 |
|---|---|---|
| 建议可以开干 | 开干 YES；blockers 空 | 可 AI 改业务；合并前仍人工审；大仓可再盯 gold_ratio |
| 建议暂缓 · 缺 fill-plan / 有开放批次 | Plan 未关 | `--init` / 继续 agents 关批次 |
| 建议暂缓 · coverage_ready=false | 诊断台覆盖条红/缺口 | 补 inventory + 分域真相 |
| 建议暂缓 · semantic_ready=false | 通用模板 / DTO 错挂 | 按接口重填再 acceptance |
| 建议暂缓 · skeleton_ready=false | 阶梯未到 L4 | resume / upgrade 到 L4 |
| 建议暂缓 · gate blockers | TODO / 形态地板 / warnings | 清 gate 项；勿只追形态分 |
| 形态已贴公式上限但开干 NO | 诊断台贴顶、趋势参考分高 | 关 Plan / 过语义 / 清 gate |

### 6.4 阶梯自检（脚手架维度）

| 阶 | 你得到什么 | 粗检 |
|---|---|---|
| L0 协作入口 | AGENTS、meta、总览规则 | 新 Agent 找得到命令与红线占位 |
| L1 契约骨架 | 所选域 docs + sync rules | 改契约有 path rule 提醒回写 |
| L2 知识回流 | agent-kb 四件套 | pitfalls 含「域」列 |
| L3 规划与软门禁 | superpowers + hooks / githooks | 软提醒不拦截提交 |
| L4 工具连接样例 | mcp example + 说明 + gitignore | 无明文密码入库 |
| L5 配置 SSOT | agent-config + sync --check | 生成物勿手改、无漂移 |

大仓常见起步：**一次到 L4**，再填真相；多工具仓再考虑 L5。阶梯齐套只是仪表盘 `skeleton_ready` 的前提之一。

### 6.5 开干仍须人工审

即使决策台为 **「建议可以开干」**，含义是「建议可以开始用 AI 改业务」，**不是**保证无错。合并前仍应审契约与代码；启发式（`quality: heuristic`）片段不得冒充已晋升的 SSOT。

## 7. 常见问题（FAQ）

### Q1：装了技能但对话里没反应？

确认技能目录在宿主可加载路径；重启或新开会话；话术里**显式点名 harness-eng**（或「落地 / 流水线 / 审计」等模式词）。MATURE 仓未点名时，默认倾向只做审计。

### Q2：Agent 一直出计划不写文件？

这是设计如此。须回复确认闸门等价词（`确认` / `按计划执行` 等）。若希望同会话连续填充，首轮一并 **确认预授权**。

### Q3：会不会覆盖我手写的 AGENTS Never do？

续跑 / merge 策略下：**同名章节正文保留**，只追加缺失章节。WritePlan 里会标 `merge` / `skip`。FOREIGN 仓删除 Claude 文件必须你书面同意。

### Q4：骨架装完就能让 AI 大规模改业务吗？

不能单凭阶梯。请跑 fill-score / 开干闸，看 **`ai_coding_ready`**。仅有空壳 `01-*.md` 或未关 fill-plan 时，开干应为 NO。

### Q5：db / redis 域为什么填不下去？

需过 **填充 MCP 闸**：矩阵里对应 `{引擎}-{环境}` 达标，且（MCP 烟测 **或** live 校准）通过。未过闸应停留在骨架，先装配 MCP 或跑 calibrate-live。

### Q6：README 里好像有密钥，技能会自动删吗？

不会。只检测并列入移交 TODO，由人工处理。MCP 真密默认不进模板分发；example 与真密分离。

### Q7：多模块大仓 glob 怎么选？

大仓【推荐】**focused**（收窄到入口与确认模块），避免 alwaysApply / 宽扫拖垮上下文。分册可选 solo / few / all。

### Q8：Cursor 和其他工具规则不一致怎么办？

先看 **对齐矩阵**：Cursor / Claude / Qoder / WorkBuddy **高**；Trae **中高**；Codex **部分（P2）**，不要假定 Codex 已全量同步。

短期：不全量镜像的宿主（尤其 Codex、L0–L2）检查契约 sync 指针；L3+ 全量镜像宿主看**本宿主** `*-sync*` 规则，不必再强求 `1x-contract-sync`。权威是根 `AGENTS.md` + `docs/**`，不是「必须以 `.cursor/rules/11|12|13|16` 为准」。长期：升 **L5**，以 `docs/agent-config/` 为 SSOT，用 `sync.mjs --check` 防漂移。

### Q9：Qoder / Trae 为什么不用 Cursor 式 hooks？

它们走 **Claude 族**协议（`settings.json` 或 `.trae/hooks.json` + `claude-adapter.js`），**有 hooks**，只是事件名与 Cursor 不同。勿把 Qoder 当成 Cursor 写 `beforeShellExecution`。Claude 族含 `claude` / `qoder` / `trae` / `workbuddy`；L3 另有 `.githooks` 兜底。

### Q10：打分 overall 很高但开干仍是 NO？

常见原因：fill-plan 未关、覆盖按 policy 未达标、acceptance blocker、gate 扫到 TODO、缺 inventory 导致覆盖不完整等。以报告 **blockers** 列表为准，按提示继续 agents / 合批 / 升 policy，而不是继续堆空文档。

### Q11：heuristic 草稿能直接当正式契约吗？

不能。须过 **acceptance-check** 再 merge；启发式须标 `quality: heuristic` 并留在 `.fill-work`，不得无标晋升 SSOT（含 jobs 的 scheduler_link=heuristic）。

### Q12：版本以谁为准？

技能版本看 `templates/_meta/manifest.yaml` 的 `version`（当前文档按 **0.6.1-dev**）与目标仓 `skill_version`。报告对照 **`skill_version` + `report_schema`**（JSON 仍暴露 `ui.version` 同值）。**报告壳版本 ≠ skill**。

### Q13：只想审计、怕写错兄弟仓？

说「审计」；多根时先确认 `Q_TARGET_ROOT`。审计默认不写盘；`write-meta-only` 等例外须你点名。

### Q14：流水线和落地有什么区别？

- **落地 land**：按目标阶梯安装/合并骨架。  
- **流水线 pipeline**：一次确认串联审计 → L4 骨架 → MCP 闸 → inventory → fill-plan → agents → score（大仓首次【推荐】）。  
半成品用 **续跑**；已成熟默认 **审计**。

# release-eng 一分钟导读

> 版本：**0.3.33**（以 `_meta/manifest.yaml` 为准）

给负责发版 / 被问「这版改了什么」的同学。完整版见 [使用手册.md](使用手册.md) · 浏览器版 [使用手册.html](使用手册.html)；Agent 入口见 [QUICKSTART.md](../QUICKSTART.md)。

## 它是什么

一套 **发版仪式**：把「这次上线」做成一份带 Git 证据的发版单——读分支对的实际改动 → 挑出 SQL / 配置 / 定时任务 → 配说明 → 落成目录包 → 上线后归档。

它**不写代码、不改生产**：不跑 SQL、不动配置、不替你决定要不要上。只负责「清单对不对、证据全不全、该归档的归档了没」。

## 解决什么

- 发版靠人肉记忆：谁改了什么、配置动没动、SQL 跑了哪几条，全在几个人脑子里
- 上线清单散在 commit 里：上线前才翻 `git log`，边翻边漏
- 配置和 SQL 靠翻代码：prod 改哪个键、哪条 migration 是本版的，一个个开文件看
- 归档无从追溯：半年前那版什么时候上的、谁上的，查不到

## 怎么用

1. **装**：让 Agent 装到你当前宿主的用户级 skills 目录（`https://github.com/18360732385/skills/tree/main/release-eng`），**必须整目录**（含 `fixtures/`、`scripts/`、`modes/`）。装完**新开会话**点名 **release-eng**。
2. **说「准备发版单」**。回答三件事：发版日期（默认「≥今天+2 的第一个周四」）、发版分支（默认 `release`）、基线分支（默认 `main`；首次发版填 `无`）。
3. **过 push-gate**：它查 `origin` 上有没有未推送的提交。没推完就停在这儿——这是硬闸，不是建议。
4. **审清单**：它 freeze 出 Git 二表 + SQL / 配置 / 任务三类候选，逐批问你（每批 ≤5，可回「全部推荐」）。看到最后的 WritePlan 预览，回 **`确认`**（或 `按计划执行` / `LGTM`）才落盘。
5. **上线后说「归档」**：它先体检（seal-check），通过后把整个目录包移进 `archive/` 并更新两个索引。

日常还可以说：「继续上次的发版单」续跑、「审计一下」只读体检、「确认预授权」让同会话后续自动落盘。

## 三条硬规则

1. **首问齐才进 push-gate**——日期 + 发版分支 +（基线或首次发版）三项回显确认过才往下走，领导口述也要回显。
2. **确认词才写盘**——只认 `确认` / `确认写入` / `按计划执行` / `执行 WritePlan` / `LGTM`；「继续吧」「👍」不算。`audit` 永不写盘。
3. **非 harness land**——不对齐工程化流水线；跨仓靠整目录拷贝 + 点名仪式。

## 怎样算可以定版

两道条件同时成立：

| 条件 | 怎么确认 |
|---|---|
| **push-gate 通过** | 两侧都有 `origin/<分支>`，且相对 origin 未推送 = 0（首次发版只验发版分支） |
| **WritePlan 已确认** | draft 预览贴出来了，且你回了词表内的确认（或预授权） |

两个都不是「看一眼觉得没问题」——第一个是 `git` 事实，第二个是白纸黑字。

## 三个最容易踩的坑

| 坑 | 真相 |
|---|---|
| 「先落盘给评审，push 稍后补」 | 不行。未通过 = 模式中止；草稿贴聊天 / gist，别写目录包 |
| 「旧单以后再 archive」 | 逾期已定版是硬闸，先 seal。要跳过必须**书面**说明，口头无效 |
| 「手工文件放 `sql/` 里」 | note-merge 刷新会先清空 `sql/` `config/` `jobs/` 再重建，手工内容请放发版单的人工段 |

## 记住三句话

1. **首问齐才进 push-gate**：别在参数没确认时就开始采集。
2. **确认词才写盘**：「继续吧」不是确认。
3. **逾期先 seal，不让旧单躺着**：进行中目录不该堆着过期的已定版单。
